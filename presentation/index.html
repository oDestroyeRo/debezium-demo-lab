1. Synchronous vs asynchronous communication

Sync blocks now. Async delivers later.

Synchronous calls are easy to reason about until latency, retries, and timeout ambiguity spread across services. Async reduces coupling, but correctness moves into delivery, ordering, idempotency, and observability.

Synchronous

  • Caller waits for callee
  • Latency chains across services
  • Timeouts create unknown state
  • Retries can duplicate side effects

Asynchronous

  • Caller commits local state first
  • Consumers react independently
  • Backpressure moves to brokers
  • Handlers must be idempotent

2. What is the dual write problem?

Two commits. One request. No shared transaction.

A Go service writes business state to MongoDB, then publishes a Kafka event. The database and broker do not share a transaction, so every error path can leave one side committed without the other. 

func CompleteCheckout(ctx context.Context, cmd Command) error {
  orderID := orders.Insert(ctx, cmd)       // MongoDB commit
  return producer.Publish(ctx, Event{      // Kafka publish
    Type: "order.completed",
    AggregateID: orderID,
  })
}
1. MongoDB write succeeds
2. Process crashes
3. Kafka event never appears
4. Downstream service waits forever

3. Why database + Kafka can become inconsistent

Failure timing decides the truth.

The hard part is the gray area: the service may not know whether Kafka accepted the event, whether retry is safe, or whether consumers already observed it.

DB commit succeeds, publish fails

MongoDB has the order. Kafka has no event. Consumers miss the transition.

Publish succeeds, response times out

The service retries. Kafka may get a duplicate event unless the producer and consumer enforce idempotency.

Publish succeeds, DB rolls back

Kafka announces state that never committed. Consumers build behavior from a false fact.

Recovery script republishes badly

Manual repair can reorder events, skip headers, or use a payload shape consumers do not expect.

4. Outbox Pattern

Commit state and event intent together.

The service no longer writes MongoDB and Kafka directly. It writes the business document and an outbox document together. The commit boundary becomes one database operation.

  • Business data and event intent commit together.
  • Kafka publishing can lag without losing the event.
  • Consumers still need idempotency because delivery can repeat.

orders

outbox_events

  "aggregatetype": "orders",
  "aggregateid": "ord_2048",
  "type": "order.completed",
  "occurred_at": "2026-06-04T04:00:00Z",

    "event_id": "evt_9182",
    "order_id": "ord_2048"
  }
}

Outbox mechanics

Service writes intent. Debezium publishes it.

API request Complete checkout
Go service Validate command
MongoDB transaction Insert order + outbox
CDC relay Read committed outbox
Kafka topic Publish event

Debezium is the relay in this deck. It does not replace the outbox write; it observes the committed outbox document and emits it to Kafka.

5. How Debezium solves it

Debezium streams committed MongoDB changes into Kafka.

A Debezium MongoDB connector watches collection changes after they commit. With an outbox collection, that means event intent becomes a durable source for Kafka publication.

  • Connector restarts from stored offsets.
  • Kafka Connect handles connector lifecycle and scaling boundaries.
  • Confluent Kafka becomes the delivery surface for downstream services.

Connector shape

{
  "connector.class": "io.debezium.connector.mongodb.MongoDbConnector",
  "mongodb.connection.string": "mongodb://mongo:27017/?replicaSet=rs0",
  "topic.prefix": "demo",
  "database.include.list": "checkout",
  "collection.include.list": "checkout.outbox_events",
  "capture.mode": "change_streams_update_full",
  "transforms.outbox.route.topic.replacement":
    "${routedByValue}.events.v1"
}

Consumer responsibility

Debezium improves delivery, but consumers still own idempotency.

CDC can replay after restarts, rebalance, or offset recovery. The consumer should treat duplicate event ids as normal and safe. 

func Handle(ctx context.Context, event Event) error {
  duplicate := inbox.InsertProcessedEvent(ctx, event.ID)
  if duplicate {
    return nil
  }

  return fulfillments.Start(ctx, event.OrderID)
}

7. Lessons learned

Durable publication is not exactly-once business behavior.

Use one commit boundary

Write domain state and event intent together in MongoDB.

Keep events boring

Stable ids, versions, aggregate keys, and timestamps make replay manageable.

Assume at-least-once delivery

Kafka consumers must dedupe by event id and be safe to retry.

Monitor the relay

Track connector status, lag, dead-letter paths, and schema drift.
